# 设计:把交付手册改写成"操作卡"体系

日期:2026-09-18
状态:待实施(实施前需用户复审)
适用:本仓库(win-linux-dualboot)全部手册与清单(本次修订后:**手册 8 份 + 1 份入口页**,按"三轨道 + 分盘前置章节"组织)
前置设计:`00-design.md`(方案本体;已随其"修订七:改用 Fedora 44 Silverblue 原子版"同步修订)、`02-fedora-atomic-variant-design.md`(原子版变体,本次文档结构调整的依据)

---

## 1. 背景:为什么要改

`00-design.md` 定稿后,手册按"六段式"(目标 / 前置条件 / 步骤 / 验证 / 失败处理 / 回滚)写成。实际读用之后暴露出五个问题(均有行号证据):

| # | 问题 | 证据 |
|---|---|---|
| P1 | **一个动作被切进四个节**:怎么做在"步骤"、"怎么算成功"又在"验证"重复一遍、"失败怎么办"在"失败处理"、"怎么退"在"回滚" | 每份文档固定六节;执行一步要在四节之间翻 |
| P2 | **编号两层混编** | `### 2. 手动分区` 内部又从 `1.` 起编子号,读者分不清"第几步" |
| P3 | **步骤是散文块而不是动作** | `04-ubuntu.md` 的 `### 1.` 约 25 行散文,夹着设计依据、评论区经验与跨节跳转 |
| P4 | **判据是表格而不是单行断言** | 步骤末尾挂三列"核对对象 / 依据 / 期望"表,一眼看不出"看到什么就算过" |
| P5 | **体量失衡且重复** | 合计约 3240 行;`07-rescue.md` 482 行、`05-first-boot.md` 436 行、`10-faq.md` 398 行;同一判据被写三遍(步骤 / 验证表 / 失败处理表) |

结论:文档**过于抽象、分步不明确、每步描述不清晰**。根因是"六段式"按**文档职责**切分,而不是按**操作者的一步动作**切分。

## 2. 目标

把手册全部改成按三轨道组织的"操作卡"体系(11 份 -> 手册 8 份 + 1 份入口页),使:

1. **一步就是一张卡**:动作、命令、判据、坑、出错去向都在同一张卡内;
2. **判据只有一处**:每步一行 `看到:`,不再有"验证表"里第三份判据;
3. **引用不再靠节名与行号**:一律用可机械校验的卡编号(`04-2`);
4. **解释性内容不复述**:依据留在 `00-design.md`,靠指针引用;
5. 总量从约 3240 行降到 **≤ 2180 行**,信息不丢(见第 8 节去向表)。

非目标(本次不做):

- **不改任何脚本的行为与接口**(`check-scripts.sh`、4 个 `.ps1`、12 个 `.sh` 一律不动);唯一例外是 `check-docs.sh` 的**校验规则**按第 6 节重写,它本身不参与部署。
- 不改 `00-design.md` 的技术决策(分区、不变量、双系统方案)。
- 不新增部署步骤,不删任何**决策级**信息(见第 8 节:依据、风险、救援、回退都必须有落点)。
- 不做 i18n(README 双语现状保留)。

## 3. 卡的格式规范

### 3.1 卡本体

```
### 04-2 手动分区:只建两块新分区,ESP 复用且不格式化
做:在安装器分区界面里,只动"未分配"那段空间。
  1. 选那段 115GiB 未分配 -> 新建 100GiB、ext4、挂载点 / 、格式化:勾
     看到:列表新增一行 100GiB ext4 /,未分配剩 15GiB
  2. 再选剩余未分配 -> 新建 15GiB、ext4、挂载点 /snapshots、格式化:勾
     看到:未分配归零
  3. 选那段 2GiB 的 EFI System -> 挂载点 /boot/efi、格式化:不勾
     看到:该行"格式化"列没有勾
坑:ESP 勾了格式化=当场毁掉 Windows 引导(设计 I3);没点安装前退回取消是无损的。
出错时:看不到磁盘 -> 01-3;ESP 已被格式化 -> 07-6。
```

### 3.2 七条硬规则

| # | 规则 |
|---|---|
| R1 | 一张卡 = 一个动作,整卡 **≤ 25 行**;超了就拆卡。计数口径:从 `### ` 行起(含),到下一个 `## ` 或 `### ` 行之前(不含),中间空行与代码块行均计入 |
| R2 | 卡标题格式 `### NN-K 动作名`,`NN` = 文档号(两位),`K` 自 1 起**连续、不跳号、不重复** |
| R3 | 卡内每个动作行后**必须**跟一行 `看到:` |
| R4 | `看到:` 必须可观测:屏幕上的具体文字、命令输出的具体行、文件/分区是否存在;禁止"确认无误""检查是否正常" |
| R5 | `坑:` 一行,写"做错会怎样";依据只给指针 `(设计 3.5)`,不复述理由 |
| R6 | `出错时:` 只给去向(卡编号或文档节),不就地展开处置 |
| R7 | `脚本:` 一行,给出本卡对应的脚本路径与 `--check`/`--apply` 组合;无法自动化的卡写 `脚本:无(人工)` 或 `脚本:无(纪律条款)` 并说明原因(细则见 `03-step-automation-design.md` 第 3 节) |

### 3.2.1 格式细则

- `做:` 行只有一条,写这一整卡要干什么;动作行用两级缩进有序列表(`  1.`),每 `看到:` 紧随其下;
- 卡内可出现表格(如分区目标值、重定向目录清单),表行计入 25 行;
- `看到:` 写屏幕上的可见结果或命令输出的关键行;无法当场观测的项(需重启后才能看到的)注明"重启后看"。

### 3.3 文档级约定

- 流程类卡文档(自检按 `0[1-7]-*.md` 的文件名范围判定;本次修订后实际为 `01`/`02`/`04`/`05`/`07`)开头固定 `## 开始前` 3–5 行:前提 / 需要的东西 / 产物落点(取代"目标 + 前置条件"两节)。其中 `07` 是**场景卡**(退役与救援),`## 开始前` 写"什么时候用这份文档、用之前必须先有什么"。
- 每份文档顶部一行定位:`本文件在流程中的位置:上一份 -> 本份 -> 下一份`。
- 文档内**不出现**"为什么这么设计"的段落;依据统一指向 `design/00-design.md`。

### 3.4 编号引用的写法

- 引用其他卡:**只允许两种写法**——`-> NN-K` 或反引号包裹的 `` `NN-K` ``;这两种是 C5 的扫描对象,其他形态的编号不会被校验(因此视为不合规);
- 引用其他文档的整份:`07-rescue.md`;
- 引用设计依据:`(设计 4.6)`、`(设计 I3)`;
- **不写**"见失败处理第 3 行""见'回滚'第 2 条"这类节名 + 序号引用。

## 5. 判据唯一化(本次改版的核心动作)

同一判据现在存在三份(步骤末表 / 验证节 / 失败处理表)。改版后:

- **判据**只在每步的 `看到:` 一行 —— 状态是"逐步判据";
- **失败处置**不写进手册正文,统一由 `07-rescue.md` 的场景卡与 `10-faq.md` 的症状卡承接;
- **回退**统一由 `checklists/rollback.md` 承接(本就有),手册只在 `出错时:` 给出编号指针;
- **整机验收**统一由 `08-verification.md` 承接(本就有),手册不再重复。
